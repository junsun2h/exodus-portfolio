# F-30. UI 성능 최적화

> **코드 발췌 없음.** 이 항목은 전역 정책 변경·조사·설계 문서 형태의 작업이라
> 특정 파일로 잘라낼 수 없다. 아래 카드의 *근거* 항목이 실제 산출물이다.

**구간** Phase 3 (2026.03.23 ~ 03.28) | **포지션** 클라 | **AI** 협업

- **문제**: UI 화면 전환과 갱신에서 프레임 드랍이 발생했다. 원인이 명확하지 않은 상태에서 "UI가 무겁다"는 인식만 있었다.
- **해결**: 특정 화면(EquipmentHUD)을 먼저 분해해 원인 3종을 특정한 뒤, 전체 UI로 확대 적용했다.
  - **`GetComponentsInChildren` 중복 호출 O(N²)** → 캐싱. 자식 순회는 호출당 비용이 크고, 갱신 루프에서 반복 호출되면 제곱으로 늘어난다.
  - **`string.Format` 박싱** → TMP **zero-alloc `SetText`**. 숫자 포맷팅은 매 프레임 GC 할당을 만든다.
  - **레이아웃 스래싱** 제거 — 레이아웃 재계산을 유발하는 연쇄 갱신 정리.
- **기술**: 컴포넌트 탐색 캐싱, TextMeshPro `SetText` zero-allocation API, 레이아웃 재계산 억제
- **정량**: 개별 화면(03.23) → 전체 UI(03.28) 순차 적용 / 명세서 2종

- **면접 포인트**: **"한 화면을 끝까지 분해한 뒤 전체로 확대한다."** 처음부터 전체 UI를 최적화하려 하면 무엇이 진짜 원인인지 알 수 없다. 한 화면에서 원인 3종을 확정하고, 그 패턴을 전체에 적용하는 순서가 문서 날짜(03.23 → 03.28)로 남아 있다. 세 가지 원인 모두 **Unity/TMP의 알려진 함정**이라 다른 프로젝트에도 그대로 이전 가능한 지식이다.
