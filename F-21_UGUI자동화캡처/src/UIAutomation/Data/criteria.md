# UI/UX 평가 기준 (Mobile Idle RPG)

> Generator-Evaluator 패턴 기반 UI 품질 평가 rubric
> 참고: [Anthropic - Harness Design for Long-Running Apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)

## 평가 방식

**두 채널 결합 평가**:
1. **시각 채널**: `UIPrefabScreenshotCapture`로 캡처한 스크린샷 (PNG)
2. **데이터 채널**: `UIYamlParser.GetPrefabStructureAsJson()`으로 추출한 구조 JSON

**Generator-Evaluator 분리 원칙**:
- UI를 만든 에이전트가 자체 평가하지 않음
- 별도 평가 에이전트가 스크린샷 + 구조 데이터로 독립 평가
- 평가 결과를 구체적 피드백으로 반환 → 개선 반복

---

## 평가 기준 (5개 항목)

### 1. 정보 계층 (Information Hierarchy) — 가중치: 높음

**정의**: 화면에서 가장 중요한 정보가 즉시 눈에 들어오고, 부차적 정보와 명확히 구분되는가

**모바일 idle RPG 맥락**:
- 전투력/스탯 등 핵심 수치가 최상위 시각 우선순위
- 재화 표시는 항상 접근 가능하되 콘텐츠를 가리지 않음
- 강화/승급 전후 비교가 한눈에 보임

**체크포인트**:
- [ ] 핵심 수치의 폰트 크기가 보조 텍스트 대비 1.5배 이상
- [ ] 주요 행동 버튼(강화, 장착, 소환 등)이 화면 하단 1/3 영역에 배치
- [ ] 탭/카테고리 전환 시 현재 선택 상태가 명확히 구분됨
- [ ] 빈 상태(empty state)에서 다음 행동이 안내됨

**안티패턴**:
- 모든 텍스트가 같은 크기/색상 → "밋밋한 정보 덩어리"
- 핵심 버튼이 스크롤 영역 안에 묻힘
- 숫자 변화(증감)에 색상/방향 표시 없음

---

### 2. 터치 적합성 (Touch Ergonomics) — 가중치: 높음

**정의**: 한 손 조작에 최적화된 터치 타겟과 간격을 갖추고 있는가

**모바일 idle RPG 맥락**:
- idle 게임은 빈번한 탭 조작 → 오탭 방지가 핵심
- 자동 진행 중 간헐적 조작 → 주의력이 낮은 상태에서도 정확한 터치

**체크포인트**:
- [ ] 모든 인터랙티브 요소의 터치 영역이 최소 44x44 (Unity 기준 RectTransform sizeDelta)
- [ ] 인접 버튼 간 최소 간격 8px 이상
- [ ] 자주 쓰는 버튼(강화, 확인)이 엄지 도달 영역(화면 하단 60%) 내 배치
- [ ] 위험한 행동(삭제, 분해)은 확인 버튼과 거리가 떨어져 있음
- [ ] 스크롤 영역 내 버튼이 스크롤 제스처와 충돌하지 않음

**데이터 채널 자동 검증 가능 항목**:
```
RectTransform.sizeDelta >= (44, 44)  — 터치 타겟 크기
인접 요소 간 anchoredPosition 차이 — 간격 검증
anchoredPosition.y 범위 — 배치 영역 확인
```

**안티패턴**:
- 닫기(X) 버튼이 너무 작거나 모서리에 붙어있음
- 리스트 아이템 내 여러 버튼이 밀집 배치
- 팝업 외부 탭으로 닫히는데 버튼과 겹침

---

### 3. 시각적 일관성 (Visual Consistency) — 가중치: 보통

**정의**: 프로젝트 전체의 색상 팔레트, 폰트 계층, 아이콘 스타일, 컴포넌트 패턴이 통일되어 있는가

**모바일 idle RPG 맥락**:
- 등급별 색상 코드가 모든 UI에서 동일 (장비, 스킬, 캐릭터)
- 버튼 색상이 행동의 의미와 매칭 (기존 rules.json 규칙 준수)
- 팝업 레이아웃 패턴이 일관적 (상단바, 닫기 위치, 하단 행동 버튼)

**체크포인트**:
- [ ] 버튼 색상이 `rules.json` 정의와 일치 (Primary=#EBC33C, Power=#C83232 등)
- [ ] 템플릿 프리팹(PXPanel_Top, PXButton_Back 등) 사용 여부
- [ ] 폰트 크기 계층: 제목(28+), 부제(22-26), 본문(18-20), 캡션(14-16)
- [ ] 팝업 구조: 상단(PXPanel_Top + 타이틀) → 콘텐츠 → 하단(행동 버튼)

**데이터 채널 자동 검증 가능 항목**:
```
Image.color 값 — rules.json 정의와 비교
TextMeshProUGUI.fontSize — 계층별 범위 확인
Nested Prefab 경로 — 템플릿 사용 여부
```

**안티패턴**:
- 같은 의미의 버튼이 화면마다 다른 색상
- 동일 계층 텍스트의 폰트 크기가 화면마다 다름
- 커스텀 구현이 템플릿 프리팹 대신 사용됨

---

### 4. 인지 부하 (Cognitive Load) — 가중치: 높음

**정의**: 한 화면에 표시되는 정보량이 적절하고, 사용자의 다음 행동이 명확한가

**모바일 idle RPG 맥락**:
- idle 게임 유저는 짧은 세션 → 빠른 판단 필요
- 강화/장착/소환 등 의사결정 지점이 명확해야 함
- 숫자가 많은 장르 → 의미 있는 숫자만 강조

**체크포인트**:
- [ ] 한 화면 내 1차 행동 버튼이 2개 이하
- [ ] 스크롤 없이 보이는 영역에 핵심 정보 포함
- [ ] 탭 개수가 5개 이하 (하단 네비게이션 포함)
- [ ] 서브 팝업 깊이가 3단계 이하
- [ ] 수치 표시에 단축 포맷 사용 (1,234,567 → 1.23M)
- [ ] "아무것도 없음" 상태에 빈 화면이 아닌 가이드 표시

**스크린샷 채널 평가 항목**:
- 시선 흐름: 화면을 처음 봤을 때 어디를 먼저 보게 되는가
- 여백: 요소 간 충분한 breathing room이 있는가
- 그룹핑: 관련 정보가 시각적으로 묶여 있는가

**안티패턴**:
- "벽돌 UI": 빈틈 없이 정보가 꽉 찬 화면
- 같은 화면에 강화 + 분해 + 합성 + 각성 버튼이 동시 노출
- 팝업 위에 팝업 위에 팝업 (3단 이상 중첩)

---

### 5. 피드백 명확성 (Feedback Clarity) — 가중치: 보통

**정의**: 사용자 행동에 대한 시각적 응답이 즉각적이고 명확한가

**모바일 idle RPG 맥락**:
- 강화 성공/실패가 즉시 체감됨
- 재화 소모 시 잔액 변화가 보임
- 비활성(disabled) 상태의 이유가 표시됨

**체크포인트**:
- [ ] 버튼 pressed/disabled 상태가 시각적으로 구분됨
- [ ] 재화 부족 시 버튼 비활성 + 부족량 표시
- [ ] 장착/해제 토글 상태가 명확
- [ ] 로딩/처리 중 상태 표시 존재
- [ ] 새로운 아이템/콘텐츠에 뱃지(red dot) 표시

**데이터 채널 검증 가능 항목**:
```
Button interactable 속성 — disabled 상태 존재 여부
CanvasGroup.alpha — 비활성 시각 처리
레드닷/뱃지 GameObject 존재 여부
```

**안티패턴**:
- 버튼을 눌렀는데 아무 반응이 없음 (비활성 표시 없이 무반응)
- 성공/실패 결과가 같은 시각적 처리
- 조건 미충족 상태에서 이유 없이 버튼만 회색

---

### 6. 재화 식별성 (Currency Legibility) — 가중치: 높음 ★ F2P 경제 화면 필수

**정의**: 화면에 표시된 재화/소모 자원이 종류별로 즉시 구분되고, 비용 라벨에 표시된 재화가 헤더 재화 중 어느 것인지 매칭되는가

**모바일 idle RPG 맥락**:
- idle RPG는 5~10종 재화가 동시 노출되는 화면이 많음 (재련/강화/소환/상점)
- 재화 식별 실패는 *오결제 → 환불 요청*과 직결 → 매출 손실 + CS 부담
- 색맹/저조도 환경에서도 구분 가능해야 함

**체크포인트**:
- [ ] 5종 이상 재화가 같은 헤더에 있을 때 **색상 + 형태 + 위치** 셋 중 둘 이상으로 구분 가능
- [ ] 모든 재화 아이콘이 동일한 동전형/동일 베이스 컬러가 아님
- [ ] 비용 라벨(예: "옵션 변경 비용 2")의 재화 아이콘이 헤더 재화 중 어느 것인지 시각적으로 매칭됨
- [ ] 재화 부족 시 잔액에 빨간색/물음표 등 시각 hook
- [ ] 재화 단위 표기(콤마/한국식 만 단위/축약)가 한 화면 내 일관됨
- [ ] 색맹 시뮬레이션(Protanopia/Deuteranopia)에서 5종이 여전히 구분 가능

**안티패턴**:
- 모든 재화가 보라색 동전 (이 화면처럼)
- "1.25만 / 8,520 / 3,740" 처럼 단위 표기 혼합
- 비용 라벨 옆 아이콘이 헤더 어느 슬롯에서도 안 찾아짐
- 재화 아이콘 차이가 *글로우 강도*만 다름 (같은 형태)

---

### 7. 확률·수치 표기 신뢰성 (Probability/Number Trust) — 가중치: 높음 ★ F2P 경제 화면 필수

**정의**: 확률/소수점/단위 표기가 일관적이고, 유저가 의사결정에 필요한 복합 수치(예: 그룹 확률 × 옵션 확률)를 직접 계산하지 않아도 되는가. 한국 공정위 확률 표기 가이드를 충족하는가

**모바일 idle RPG 맥락**:
- 한국 공정위 가이드: 모든 확률 아이템은 확률 명시 의무 (2024 시행)
- 복합 확률을 유저가 직접 곱셈해야 한다면 **신뢰감 결손 + 환불 사유**
- 출시 전 누락 시 *법적 리스크*

**체크포인트**:
- [ ] 모든 확률이 합산 100% (또는 의도적 비합산이라면 명시)
- [ ] 복합 확률(그룹 × 옵션, 페이즈 × 슬롯 등) 결과를 별도 칼럼으로 직접 표시
- [ ] 그룹 헤더의 확률 라벨이 *무엇의 확률*인지 한 단어로 명시 (예: "이 그룹이 뽑힐 확률 7.4%")
- [ ] 소수점 자릿수 일관 (50.00 / 7.99 / 2.0% 혼용 X)
- [ ] 단위(`%`, `+`, `×`) 표기 일관
- [ ] 확률 표기 위치가 *시선 동선*에 맞음 (값 옆 또는 같은 행)
- [ ] (경제 화면 한정) 환불 불가 / 결과 적용 안내 명시

**안티패턴**:
- "확률 7.4%"가 무엇을 가리키는지 화면만 보고 모름
- 50.00% / 8.0% / 2% 처럼 소수점 자리 혼합
- 그룹별 가중치가 합쳐서 100%가 안 됨
- "값(최대) 50%"가 *어떤 효과의 50%인지* 표 안에서 모름
- 결과 직전 확인 단계 없이 바로 차감

## 채점 방식

### 5점 척도

| 점수 | 의미 | 설명 |
|------|------|------|
| 5 | Excellent | 장르 레퍼런스 수준, 개선 여지 거의 없음 |
| 4 | Good | 핵심 기준 충족, 사소한 개선 여지 |
| 3 | Acceptable | 기능적으로 문제없으나 UX 마찰 존재 |
| 2 | Needs Work | 명확한 문제가 있어 사용자 이탈 유발 가능 |
| 1 | Critical | 기본 사용이 어려운 수준 |

### 가중 점수 계산

```
총점 = (정보계층 × 3 + 터치적합성 × 3 + 시각일관성 × 2 + 인지부하 × 3 + 피드백명확성 × 2
       + 재화식별성 × 3 + 확률신뢰성 × 3) / 19
```

> 항목 6, 7은 **F2P 경제 화면**(재련/강화/소환/상점/뽑기/패스 등)에서만 ×3 적용. 비경제 화면(전투·소셜·메타·튜토리얼)에서는 두 항목을 제외하고 분모를 13으로 한다.

### 합격 기준

- **총점 3.5 이상**: 출시 가능 (일반 화면)
- **총점 4.0 이상**: 출시 가능 (경제 화면) — 매출 핵심이라 더 빡빡함
- **총점 3.0~3.5**: 개선 권장
- **총점 3.0 미만**: 개선 필수

### 자동 FAIL 룰 (★ 무조건)

**다음 중 하나라도 해당하면 합격선과 무관하게 FAIL**:
- 어느 항목이라도 **점수 ≤ 2**
- 경제 화면인데 항목 6(재화식별성) 또는 항목 7(확률신뢰성) 점수 ≤ 3
- AI 슬롭 누적 감점이 -1.5 초과
- 한국 공정위 확률 표기 가이드 위반 (확률 명시 누락 등)

## 장르 레퍼런스

평가 시 다음 게임들의 UI를 기준점으로 참고:

| 게임 | 참고 포인트 |
|------|-----------|
| AFK Arena | 캐릭터 상세 화면 정보 계층, 영웅 목록 그리드 |
| Nikke | 로비 네비게이션 단순성, 하단바 구조 |
| Solo Leveling: Arise | 장비 강화 UX 흐름, 스탯 비교 표시 |
| 원신 | 인벤토리 필터/정렬 UX, 캐릭터 상세 탭 구조 |

> 이 레퍼런스는 "똑같이 만들어라"가 아니라 "이 수준의 UX 품질을 목표로 하라"는 기준점
