# F-38. Cloud Functions 라운드트립 감축

**구간** Phase 3 (2026.04.06) | **포지션** 서버 | **AI** 협업

- **문제**: 장비 재련 API의 응답이 느렸다. "서버가 느리다"는 인식은 있었지만 **어디가 느린지**를 몰랐다.
- **해결**: 단일 API 흐름을 **9단계로 해부**해 각 단계의 비용을 측정하고, **순차 Firestore 라운드트립 6회(300~700ms)**를 병목으로 특정했다. Firestore 왕복은 한 번당 수십~백 ms이고, 이것이 순차로 6번 쌓이면 그대로 응답 시간이 된다.
  - 특정 후 **4개 최적화 작업으로 분할**해 각각 별도 계획으로 진행했다:
    - `checkServerStatus` 모듈 레벨 메모리 캐시
    - `validateRequestWithRateLimit` PUID 경량 문서 분리
    - 장비 재련 API 실제 구동 환경 최적화
    - 장비 재련 추가 최적화
- **기술**: API 흐름 단계별 계측, Firestore 라운드트립 분석, 모듈 레벨 캐시(콜드스타트 간 재사용), 문서 분리로 읽기 비용 감축
- **정량**: 9단계 해부 / 라운드트립 **6회 300~700ms** 식별 / 최적화 계획 4종

- **면접 포인트**: **서버리스 성능 최적화의 특수성.** 서버리스에서 병목은 CPU가 아니라 **DB 라운드트립과 콜드스타트**다. 9단계 해부로 그것을 정확히 특정했고, `checkServerStatus`를 **모듈 레벨**에 캐시한 것은 서버리스 인스턴스 재사용 특성을 이용한 최적화다(요청 간 메모리가 살아 있다). 하나의 분석 문서에서 4개 실행 계획이 파생된 구조도 특징 — **측정 → 분해 → 개별 실행**.
