# Firebase Functions 메모리 최적화 계획

## 핵심 문제: 정적 Import로 인한 메모리 비효율

### 문제 상황

현재 `index.ts` 구조:
```
index.ts (361줄)
├── 32개의 정적 import 문 (모든 API 모듈)
└── 100개 함수 export (onCall 98개 + onSchedule 2개)
```

**문제점**: `Request_Account_Login` 하나만 호출해도:
- ServerOperation 모듈 전체 (~1.2MB)
- Schedule 모듈
- DataBundle 모듈
- 기타 모든 CoreData 모듈

등 **사용하지 않는 모든 코드가 메모리에 로드됨**

### 영향 범위

| 함수 분류 | 개수 | 메모리 설정 | 정적 Import 영향 |
|----------|------|------------|-----------------|
| LITE | 58개 | 256MiB | **가장 영향 큼** (여유 없음) |
| STANDARD | 14개 | 512MiB | 영향 있음 |
| HEAVY | 23개 | 1GiB | 상대적으로 여유 |
| SCHEDULE | 5개 | 1GiB | 상대적으로 여유 |

**핵심**: LITE 함수 58개가 256MiB 제한에서 불필요한 모듈까지 로드하면서 메모리 압박 발생

## 구현 패턴

### 권장: Factory 헬퍼 함수 패턴

```typescript
// index.ts 상단에 추가 (setGlobalOptions 아래)

// 동적 import를 위한 헬퍼 함수 - 모듈을 실제 호출 시점에 로드하여 메모리 최적화
function lazyHandler(modulePath: string, handlerName: string) {
    return async (request: https.CallableRequest<any>) => {
        const module = await import(modulePath);
        if (!module[handlerName]) {
            throw new Error(`[DYNAMIC_IMPORT_ERROR] Handler ${handlerName} not found in ${modulePath}`);
        }
        return await module[handlerName](request);
    };
}
```

### 적용 예시

**변경 전 (정적 import)**:
```typescript
// 상단 import
import { request_ServerNotice_Create, ... } from "./API/ServerOperation/ServerNotice";

// export
export const Request_ServerNotice_Create = https.onCall(
    setV2FunctionPreset(V2_Functions_Preset.LITE),
    request_ServerNotice_Create
);
```

**변경 후 (동적 import)**:
```typescript
// 상단 import 제거

// export - lazyHandler 사용
export const Request_ServerNotice_Create = https.onCall(
    setV2FunctionPreset(V2_Functions_Preset.LITE),
    lazyHandler("./API/ServerOperation/ServerNotice", "request_ServerNotice_Create")
);
```

### Schedule 함수용 패턴

```typescript
export const scheduledFunction_ServerMailbox_DeleteExpired = onSchedule(
    {
        schedule: `*/${GameGlobalConfig.schedule_ServerMailbox_DeleteExpired_Minutes} * * * *`,
        ...setV2FunctionPreset(V2_Functions_Preset.SCHEDULE),
    },
    async () => {
        const { CServerMailboxDeleteExpired } = await import("./API/Schedule/ScheduleFunction");
        const { CServerInternalBase } = await import("./API/Base/ServerInternalBase");
        await CServerInternalBase.createInternalFunction(CServerMailboxDeleteExpired)();
    }
);
```

## 예상 효과

### 정량적 분석

| 항목 | 현재 (정적) | 적용 후 (동적) | 개선 |
|-----|------------|---------------|------|
| Cold Start 메모리 | ~10-12MB | ~8.5-10.5MB | **10-15%** |
| ServerOperation 모듈 | 항상 로드 | 호출 시 로드 | 100% 지연 |
| LITE 함수 안정성 | 메모리 압박 | 개선 | - |

### Cold Start 시간 영향

| 시나리오 | 예상 영향 |
|---------|---------|
| CoreData 함수 호출 | 변화 없음 (정적 유지) |
| ServerOperation 함수 첫 호출 | +50-150ms (모듈 로딩) |
| ServerOperation 함수 재호출 | 변화 없음 (캐시됨) |

**결론**: 관리자 전용 함수는 응답 시간 민감도가 낮으므로 허용 가능한 트레이드오프

## 리스크 및 완화 방안

| 리스크 | 영향도 | 완화 전략 |
|--------|--------|----------|
| Cold Start 지연 | 중 | 관리자 함수 대상으로 한정 (사용자 대면 X) |

## 향후 전략: 도메인 분리 (장기)

**목표**: 완전한 격리를 통한 최대 메모리 최적화

### 분리 구조 제안

```
functions/
├── account-functions/          # 계정 관리 (독립)
│   └── Account, Auth, Migration (7개 함수)
│
├── game-functions/             # 게임 플레이 핵심
│   └── Stage, Player, Currency, Quest (21개 함수)
│
├── collection-functions/       # 수집 시스템
│   └── Equipment, Skill, Pet, Awaken, Craft (45개 함수)
│
├── commerce-functions/         # 상거래
│   └── Product, Mailbox (12개 함수)
│
└── admin-functions/           # 관리 기능
    └── ServerOperation 전체 (21개 함수)
```

### 의존성 그래프

```
[높은 의존성 - 분리 어려움]
Stage ← Player ← Equipment ← Skill ← Pet
         ↑
       Currency ← Product ← Mailbox ← Quest

[중간 의존성]
Awaken ← Equipment, Skill, Player
Nebula ← Currency, Player
Craft ← Equipment, Skill, Currency

[낮은 의존성 - 분리 용이]
Account (독립)
Auth (독립)
Migration (독립)
ServerOperation 전체 (관리자 기능)
```
