# Docs 위키 자동 생성 Skill

코드 작업 중 발견한 시스템/메커니즘을 분석하여 Docs/ 내 적절한 위치에 위키 문서를 생성하고 INDEX.md를 갱신한다.

## 트리거

- `/docs-addwiki` — 대화 컨텍스트에서 문서화할 대상 파악
- `/docs-addwiki 장비강화 Pity 시스템` — 주제를 직접 지정
- 작업 중 "이거 위키로 정리해줘", "문서화해줘" 등의 요청

## 절차

### 1단계: 대상 파악

문서화할 시스템/메커니즘의 핵심을 파악한다:
- 대화 컨텍스트에서 어떤 시스템인지 확인
- 관련 코드 파일을 읽어 동작 방식 이해
- 관련 GameDB 테이블이 있으면 구조 파악

사용자가 이미 설명했거나 코드를 보여준 경우, 추가 질문 없이 진행한다.

### 2단계: 분류 결정

`Docs/INDEX.md`를 읽고 아래 분류표에서 가장 적합한 위치를 결정한다.

| 시스템 성격 | Docs 경로 | INDEX 섹션 |
|------------|----------|-----------|
| 전투/배틀 메커니즘 | `배틀/_기획/위키/` | 배틀 — 기획 위키 > 핵심 메커니즘 |
| 투사체/주문 관련 | `배틀/_기획/위키/주문/` | 배틀 — 기획 위키 > 투사체/주문 |
| 오라 관련 | `배틀/_기획/위키/오라/` | 배틀 — 기획 위키 > 오라 위키 |
| MOD 관련 | `배틀/_기획/위키/mod/` 또는 `배틀/_기획/mod/` | 배틀 — 기획 위키 > MOD 기획 |
| 콘텐츠 시스템 (장비, 성좌, 퀘스트 등) | `콘텐츠/{시스템명}/` | 콘텐츠 — 시스템 설계 |
| 상품/BM 관련 | `상품/` 하위 | 상품 — 기준문서 |
| 인프라/도구 | `인프라/` 하위 | 인프라 — 시스템/도구 가이드 |
| 코드 구조 분석 | `레퍼런스/클라-분석/` | 클라-분석 — 코드 구조 분석 |
| 프로젝트 공통 규칙 | `레퍼런스/` | 레퍼런스 — 프로젝트 공통 규칙 |

**판단 기준**:
- 기존 INDEX.md의 키워드와 매칭되는 섹션이 있으면 그 근처에 배치
- 여러 섹션에 걸치면 **핵심 기능**이 속하는 쪽을 택한다
- 기존 카테고리에 맞지 않으면 가장 가까운 상위 카테고리에 배치

분류가 애매하면 사용자에게 한 번만 확인한다: "이 시스템은 `배틀/_기획/위키/`에 넣으려 합니다. 맞나요?"

### 3단계: 파일명 결정

```
{YY.MM.DD}_위키_{시스템명}.md
```

- 날짜: 오늘 날짜 (예: `26.04.10`)
- 시스템명: 한글, 필요시 영문 병기 (예: `장비강화_연속실패보정(Pity)`)
- 공백 대신 `_` 사용

### 4단계: 문서 작성

아래 구조를 기본으로 하되, 시스템 성격에 맞게 유연하게 조정한다.

```markdown
# {시스템 한글명} ({영문명})

## 개요

{1~3줄로 시스템의 목적과 핵심 동작 요약}

## 동작 규칙

{핵심 규칙을 번호 목록으로. 코드에서 파악한 실제 동작 기준}

## 데이터 구조

### GameDB: {테이블명} (있는 경우)

{테이블 필드 설명}

### CoreData: {타입명} (있는 경우)

{관련 필드 설명}

## 서버 구현 (서버 로직이 있는 경우)

**파일**: `{경로}`

{핵심 함수와 동작 흐름 요약. 코드 복붙이 아닌 로직 설명}

## 클라이언트 (UI/표시 로직이 있는 경우)

{유저에게 보이는 동작}

## 흐름도 (복잡한 시스템인 경우)

{텍스트 기반 플로우차트}

## 비고

{예외 케이스, 주의사항, 향후 변경 가능성 등}
```

**작성 원칙**:
- **설계 의도와 규칙** 중심. 코드 시그니처/파라미터 목록은 쓰지 않는다
- 함수명·라인번호는 참조용으로만 간략히 기재 (변경될 수 있으므로)
- GameDB 필드, CoreData 필드는 테이블로 정리
- 공식이 있으면 코드블록으로 표기
- 불필요한 섹션은 생략한다 (서버 없으면 서버 섹션 제거 등)

### 5단계: INDEX.md 갱신

1. 해당 카테고리 섹션의 테이블에 새 항목 추가
2. 형식: `| [문서제목](상대경로) | 한 줄 설명 | 키워드1, 키워드2 |`
3. 키워드는 INDEX 검색에 활용되므로, 코드에서 쓰이는 영문 식별자 + 한글 개념어 포함
4. `마지막 갱신:` 날짜를 오늘로 업데이트

### 6단계: 검증

1. 생성된 문서를 다시 Read하여 내용 확인
2. INDEX.md를 다시 Read하여 항목이 올바른 섹션에 추가되었는지 확인
3. 결과 보고:
   ```
   위키 생성 완료:
   - 파일: Docs/{경로}/{파일명}.md
   - INDEX 섹션: {섹션명}
   - 키워드: {키워드 목록}
   ```

## 일괄 생성

여러 시스템을 한 번에 문서화할 때는 각각에 대해 2~5단계를 반복하되, INDEX 갱신은 마지막에 한 번만 수행한다.

## 주의사항

- 이미 INDEX.md에 동일/유사 문서가 있으면 사용자에게 알린다 ("기존 문서가 있습니다: {경로}. 새로 만들까요, 기존 문서를 갱신할까요?")
- 코드에서 읽어낸 **현재 구현 기준**으로 작성한다. 추측이나 일반론을 넣지 않는다
- 날짜 접두사는 문서 생성일이지 시스템 구현일이 아니다
