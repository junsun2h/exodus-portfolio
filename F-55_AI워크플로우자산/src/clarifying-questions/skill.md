# Clarifying Questions Skill

작업 시작 전, 의도가 모호한 부분을 질문으로 메우고 명세를 합의한 뒤에만 코드를 만진다.

## 핵심 원칙

**"잘못된 방향으로 빠르게 가는 것보다, 옳은 방향을 1분 늦게 시작하는 게 낫다."**

LLM은 모호한 요청을 받으면 그럴듯한 해석 하나를 골라 즉시 실행하는 경향이 강함. 그 해석이 틀리면 30분~2시간 작업이 통째로 버려짐. 질문 1~2개로 5분 안에 막을 수 있는 일.

## 발동 트리거 (Y면 질문, N이면 즉시 진행)

다음 중 **하나라도** 해당되면 시작 전 질문:

- [ ] 작업 추정이 5분 이상
- [ ] 추상 동사 포함: "개선/정리/최적화/리팩토링/폴리싱/다듬어/손봐"
- [ ] 영향 범위가 여러 파일 / 여러 시스템
- [ ] "어떻게 끝났다고 판단할지"가 명백하지 않음
- [ ] 여러 해석 가능한 단어 ("UI 폴리싱", "성능 개선", "구조 개선")
- [ ] 산출물 형태가 모호 (문서? 코드? 둘 다?)
- [ ] 사용자가 새로운 도메인/패턴/도구를 처음 언급

## 즉시 진행 조건 (질문 금지)

다음에 해당하면 묻지 말고 바로 실행:

- 단일 파일/단일 함수의 명확한 수정 (예: "X 함수의 Y를 Z로 바꿔줘")
- 사용자가 이미 정확한 명세 제공
- 읽기/탐색/검색 작업
- 5분 이내 완료가 명백
- 슬래시 커맨드 (`/...`) 실행 — 사용자가 이미 의도 표현
- 사용자 메모리에 "확인 없이 바로 진행" 룰 적용 대상 (커맨드 실행류)

## 질문의 형태 · 안티패턴 · 워크플로우

좋은 질문 형태(객관식 우선, 1~3개 제한, 가정 명시, 영향 범위/검증 기준 함께 묻기), 피해야 할 안티패턴, 전체 워크플로우 다이어그램 등 구체 예시는 [examples.md](examples.md) 참조.

핵심만: 질문은 **객관식 + 가정 명시** 형태로 **1~3개**. 답변 후 실행 직전 아래 "합의 재확인 형식"으로 한 번 못박는다.

## 합의 재확인 형식

질문 답변 후 실행 직전:

```
명세 정리:
- 목표: {한 줄}
- 만질 파일: {목록 또는 범위}
- 만지지 않을 것: {스코프 외}
- 검증 방법: {어떻게 끝났는지 알 수 있나}
진행하겠습니다.
```

이 한 블록만 있으면 사용자가 마지막으로 점검 가능 + 나중에 스코프 다툼 방지.

## 효과 (도입 사유)

1. **잘못된 방향 조기 차단** — 90%의 가치가 여기서 나옴
2. **사용자 암묵 가정 표면화** — 사용자도 자기 요구를 더 잘 이해하게 됨
3. **스코프 합의** — "겸사겸사 이것도" 차단
4. **검증 기준 사전 합의** — 완료 시점 모호함 제거 (`verification-before-completion`과 짝)
5. **저렴한 실패** — 질문 단계 비용 = 대화 몇 줄, 코드 만진 후 잘못 알아채는 것보다 100배 저렴

## 단점 인지

- 자명한 요청에 질문하면 짜증남 → **트리거 엄격히 적용**
- 매 요청마다 1~2턴 추가 → 5분 이상 작업에만 한정
- flow state 방해 가능 → 짧고 객관식으로

## 관련

- `verification-before-completion` — 사전 합의한 검증 기준을 완료 시 사용
- `systematic-debugging` — 작업 중 막히면 발동
- 사용자 메모리 `feedback_no_confirm.md` — 커맨드 실행류는 질문 금지 (이 스킬과 충돌하지 않음)
