## Portfolio Generation
When generating product portfolio documents (5-file sets), be mindful of output token limits. If a document is likely to be long (e.g., subscription or overview docs), write it in a separate step rather than combining with other documents in parallel agent tasks.

When adjusting game economy values (efficiency targets, pricing, quantities), always maintain the user's stated target metrics (e.g., '300% efficiency') by back-solving quantities — do NOT hold quantities fixed and recalculate efficiency.

## 작업 절차

> **Context 최적화 원칙**: 기준문서를 main context에 쌓지 않는다. 각 작성 에이전트가 자기에게 필요한 문서만 직접 읽는다 ("읽기 분리, 경로만 전달").

### Phase 0: 차수 확인 + 폴더 생성

`<project-root>\Docs\상품\포트폴리오\` 에서 기존 차수 확인 후 N+1차 폴더 생성.
패키지 하위 폴더도 함께 생성: `N차/YY.MM.DD_3.상품설계_패키지/`

### Phase 1: Main Agent 최소 읽기 + 설계 결정

Main agent가 읽는 파일을 **2개로 제한**:

| 파일 | 목적 |
|------|------|
| `기준문서/공통/02_수익화_원칙.md` | 효율 가이드라인 |
| `기준문서/참조/01_재화가치_기준.md` | 가치 환산 기준 |

**금지**: 카테고리별 규칙(`카테고리/*`), 콘텐츠_특화(`참조/03`), 트리거(`참조/04_트리거`), 세계관(`참조/04_세계관`), 공통_규칙(`공통/03`), 네이밍(`공통/04`), 포지셔닝(`공통/01`) 등 나머지 기준문서는 main context에서 **절대 읽지 않는다**.

유저와 대화하여 이번 차수의 변경 방향을 결정한다.

### Phase 2: `_directive.md` 중간 파일 작성

이번 차수의 설계 지시사항을 중간 파일로 작성한다. 작성 에이전트들이 이 파일을 읽고 작업한다.

- **경로**: `포트폴리오/N차/_directive.md`
- **크기**: 5KB 이하 (지시사항만, 수치 직접 기재 금지)
- **내용**:
  - 메타정보 (기준문서 버전, 날짜, 차수)
  - 카테고리별 변경/유지 지시 (변경 있는 카테고리만 상세 기술)
  - 공통 적용사항
- 수치는 경로 참조 형태로 기재 (예: "`참조/01_재화가치_기준.md`의 5.3절 신화 가치 적용")
- **수치를 직접 복사하지 않는다** — 에이전트가 기준문서를 직접 읽어서 확인

### Phase 3: 작성 에이전트 병렬 실행 (최대 6개)

각 카테고리별 에이전트를 아래 매핑에 따라 실행. 패키지는 **3개 서브 에이전트로 분할**.

#### 에이전트 prompt 구조 (핵심: 경로만 전달, MD/JSON 분리 출력)

에이전트에게 파일 내용이 아닌 **절대 경로만** 전달한다. 에이전트가 직접 Read 도구로 파일을 읽는다.

**토큰 절약 원칙**: 설계 문서(MD)에는 상품 설명/검산만, 데이터는 JSON 파일에만 작성한다. **MD에 JSON/YAML 데이터 블록을 포함하지 않는다.**

**일반 에이전트 (일반상점/패스/구독권) prompt:**

```
당신은 {카테고리} 설계 문서와 uploader용 JSON 파일을 작성합니다.

## 1단계: 파일 읽기
다음 파일을 순서대로 읽으세요 (Read 도구 사용):
1. {_directive.md 절대 경로}
2. {기준문서 절대 경로 목록 — 각 파일별 한 줄씩}
3. `Tools/sheets_uploader/사용설명서.md` — JSON 포맷 참조

## 2단계: 설계 문서(MD) 작성
- _directive.md의 지시사항을 반영
- 수치/규칙은 1단계에서 읽은 기준문서에서 직접 확인하여 적용
- **MD에는 JSON/YAML 데이터 블록을 포함하지 않는다**
- 각 상품별로 다음 정보만 마크다운 텍스트로 작성:
  · 상품 설명 (역할, 타겟, 컨셉)
  · 보상 구성 요약 (표 또는 목록)
  · 검산용 정보 (보상별 다이아 환산, 총 가치, 효율 계산 과정)
  · 가격, 트리거, FOMO 조건 등

## 3단계: JSON 파일 작성
- sheets_uploader 입력 포맷 기준으로 JSON 작성
- 스키마는 아래 "JSON 스키마" 섹션 참조
- **MD 작성 내용을 다시 읽지 않고, 2단계에서 설계한 내용을 바로 JSON으로 출력**

## 4단계: 출력 (Write 도구)
1. MD 파일: {MD 출력 절대 경로}
2. JSON 파일: {JSON 출력 절대 경로} (예: passes.json, subscription.json)
```

**패키지 서브 에이전트 (A/B/C) prompt:**

```
당신은 패키지 {그룹명} 설계 문서와 JSON 파일을 작성합니다.
담당 분류: {담당 카테고리 목록}

## 1단계: 파일 읽기
다음 파일을 순서대로 읽으세요 (Read 도구 사용):
1. {_directive.md 절대 경로}
2. {기준문서 절대 경로 목록 — 각 파일별 한 줄씩}
   - 반드시 `카테고리/02_패키지/00_공통.md` + 담당 하위 문서만 읽기
3. `Tools/sheets_uploader/사용설명서.md` — JSON 포맷 참조

## 2단계: 설계 문서(MD) 작성 — 담당 카테고리별 개별 파일
- 각 카테고리마다 별도 MD 파일로 작성
- **MD에는 JSON/YAML 데이터 블록을 포함하지 않는다**
- 각 상품별: 상품 설명, 보상 구성 요약, 검산, 가격/트리거/FOMO

## 3단계: JSON 파일 작성 — 담당 카테고리별 개별 파일
- 각 카테고리마다 별도 JSON 파일로 작성
- 스키마는 "JSON 스키마" 참조, 루트 키 = "packages"

## 4단계: 출력 (Write 도구) — 모두 패키지 폴더에 저장
출력 폴더: {패키지 폴더 절대 경로}
{각 카테고리별 MD 파일명 + JSON 파일명 목록}
```

> **패키지 분할의 이점**: 기존 단일 에이전트 context 과부하 문제가 자연스럽게 해결됨.
> 각 서브 에이전트가 필요한 기준문서 하위 문서(01~08)만 읽으므로 context 효율 극대화.

### Phase 4: 개요 + 패키지 총괄 에이전트 순차 실행

**Phase 3 완료 후** 실행한다. 모든 카테고리 문서를 종합하여 개요 문서 + 패키지 총괄 문서를 작성한다.

**읽기 대상**:
- `포트폴리오/N차/_directive.md`
- 완성된 일반상점 문서 (`_2.상품설계_일반상점.md`)
- 완성된 패키지 폴더 (`_3.상품설계_패키지/01_장비.md` ~ `08_층도전.md` — 8개 MD)
- 완성된 패스/구독권 문서 (`_4.상품설계_패스.md`, `_5.상품설계_구독권.md`)
- `기준문서/공통/02_수익화_원칙.md`

**출력**:
1. `포트폴리오/N차/YY.MM.DD_1.상품설계_개요.md` — 전체 포트폴리오 개요

### 구독권 JSON 스키마 (`subscription.json`)

> 구독권 스키마는 향후 config.json 확장 시 추가. 현재는 `Tools/sheets_uploader/사용설명서.md`의 "향후 확장" 참조.

### 공통 필드 규칙

- `name`: `productpackage_` + 소문자 식별자 (패키지), `product_pass_` + 소문자 식별자 (패스)
- `payment_cost`: 쉼표 포맷 문자열 (`"1,100"`)
- `effectiveness`: 퍼센트 문자열 (`"1000%"`)
- `vip_level`: 전체 공개면 빈값, 등급 제한이면 `"shrimp"` / `"dolphin"` / `"whale"`
- `trigger_achieveitem1`: `참조/04_트리거.md`의 EAchieveItem enum명 직접 사용 (패키지 전용)
- `trigger_value1`: 조건값 숫자 (패키지 전용)
- `limit_time`: FOMO 시간(h) 숫자, 없으면 빈값 (패키지 전용)
- `to_mailbox`: 패키지는 `1`, 패스는 `""` (패스는 바로 수령)
- `enum_index`: 생략 (uploader 자동 부여)
- **패키지 아이템**: `product_ticket`에 뽑기권이면 `gacha_`/`pick_`/`fix_` 접두어 사용, `currency`는 uploader가 자동 설정. 일반 재화면 `currency` 직접 입력, `product_ticket`은 빈값
- **패스 아이템**: `free_reward_ticket`/`pass_reward_ticket`에 뽑기권이면 `gacha_`/`pick_`/`fix_` 접두어 사용, `free_reward`/`pass_reward`는 uploader가 자동 설정. 일반 재화면 `free_reward`/`pass_reward` 직접 입력, ticket은 빈값

#### "상품설계_개요" 필수 포함: 상품 총괄 요약표

**작성 규칙:**
- 각 대분류(일반상점/패키지/패스/구독권)를 하위 분류별로 분해하여 표로 정리
- 원화(₩) 직접 판매가 아닌 상품(다이아 교환, 티켓 교환, 무료/광고)은 가격 합계에 `-` 표기
- 각 대분류 테이블 마지막 행에 소계 표시
- 최종 대분류 총합계 테이블에 비중(%) 포함
- 버전과 총 상품 수를 제목에 명시

## 주의사항

- 기존 StaticGameDB 데이터는 참조하지 않음 (테스트용 데이터)
- 상품 개수에 제한 없음 - 게임에 맞게 자유롭게 설계
- **수치/규칙이 필요하면 항상 기준문서에서 참조** - skill 내 자체 수치 보유 금지
- Sequential Thinking 활용 권장 (복잡한 설계 시)
