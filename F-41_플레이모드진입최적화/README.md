# F-41. 플레이 모드 진입 최적화

**구간** Phase 3 (2026.04.22) | **포지션** 클라·TD | **AI** 협업

- **문제**: Unity 플레이 모드 진입부터 실제 게임 화면까지의 시간이 길었다. 개발 중 하루에 수십 번 반복하는 동작이라 **개발 속도에 직결**된다. 하지만 어느 단계가 느린지는 감으로 알 수 없었다.
- **해결**: **Phase 1 전체를 계측 인프라 구축에 할당했다.** 최적화를 하기 전에 `[BOOT]` 마커를 **30개 이상 지점**에 심어 각 구간 소요를 측정 가능하게 만들었다. 그다음 실제 병목을 잡았다.
  - **GameDB 이중 직렬화 제거** — `Firestore → SerializeObject → JSON.Parse → FromJson`이라는 **불필요한 왕복**이 있었다. Firestore에서 온 객체를 다시 문자열로 만들고 다시 파싱해 다시 객체로 만드는 구조. 계측이 없었다면 "GameDB 로딩이 원래 느린 것"으로 넘어갔을 부분이다.
  - **로그인 4단계 직렬 → 병렬** — 서로 의존하지 않는 로그인 단계들이 순차 실행되고 있었다.
  - 관련 작업으로 플레이 모드 **종료** 시 Firebase 대기로 인한 도메인 리로드 Busy 문제도 해결(`26.04.09`).
- **기술**: 부팅 구간 계측 마커, 직렬화 경로 분석, 비동기 병렬화, Unity 도메인 리로드 처리
- **정량**: `[BOOT]` 계측 지점 **30+개** / 이중 직렬화 4단계 → 직접 변환 / 로그인 4단계 직렬 → 병렬
