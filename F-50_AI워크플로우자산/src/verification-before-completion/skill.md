# Verification Before Completion Skill

작업 완료를 선언하기 전에 반드시 거쳐야 하는 검증 게이트. superpowers/verification-before-completion 차용.

## 절대 원칙

**"증거가 먼저, 주장은 나중 (Evidence before claims, always)"**

검증 없이 "완료" / "동작할 것" / "고쳤음"이라고 말하는 것은 효율이 아니라 부정직. 사용자는 검증되지 않은 보고를 신뢰할 수 없다.

## Verification Gate (5단계)

완료 선언 전에 반드시:

1. **Identify** — 내 주장을 증명할 명령/확인 방법을 명시
2. **Execute** — 그 명령을 **새로** 실행 (캐시된 결과 신뢰 금지)
3. **Read** — 출력 / exit code / 에러 메시지 전체를 읽는다
4. **Verify** — 결과가 실제로 주장을 뒷받침하는지 판단
5. **Report** — 그 후에만 결론을 말한다 (증거 인용 포함)

## 적용 대상

- 코드 수정 후 컴파일/빌드 통과 주장
- 테스트 작성 후 통과 주장
- 버그 수정 후 재현 안 됨 주장
- 리팩토링 후 동작 동일성 주장
- UI 변경 후 시각적 결과 주장
- 서브에이전트 작업 위임 후 결과 주장 (에이전트 보고만 신뢰 금지 — 직접 확인)

## Red Flag 표현 (이 말이 입에 떠오르면 멈춰라)

- "이제 동작할 겁니다"
- "아마 통과할 거예요"
- "고쳤습니다" (검증 없이)
- "확신합니다"
- "Should work now"

이런 말이 떠오르면 **검증 게이트 5단계로 돌아가라.**

## 우리 프로젝트 검증 명령 카탈로그

| 작업 종류 | 검증 명령 |
|---|---|
| C# 코드 수정 | MCP `refresh_unity` → `read_console(types=["error"])` (Unity 컴파일 확인) |
| Unity Editor 스크립트 동작 | MCP `execute_code(action="execute", code="...")` 으로 실제 호출 |
| 파일 edit | 변경한 파일을 **다시 Read** 해서 의도대로 들어갔는지 확인 |
| UXML/USS 수정 | UI Builder에서 캡처 → `ui-evaluate-lite` 재평가 |
| 프리팹 수정 | `ui-prefab-dirty` / `ui-evaluate-runtime` |
| 데이터 추가 | `data-upload-gamedb` 결과 로그 확인 |
| 빌드 | Unity Build → 콘솔 로그 확인 |
| Git 작업 | `git status` + `git log -1` |

## 특수 룰: Edit 무결성

- 같은 파일을 **3회 이상 연속 edit** 시 중간에 검증 Read 1회 강제
- 대화가 **10턴 이상** 지난 후 파일 edit 시 해당 파일 재 Read 강제
- 500줄 이상 파일은 부분만 본 거라고 간주하고 필요시 offset/limit 사용

(편집 안전 규칙의 완료 시점 게이트 버전.)

## 6단계: 문서 정합성 체크

검증 게이트 5단계를 통과한 후, 완료 선언 전 마지막으로 수행한다.

### 판단: 문서 갱신이 필요한 변경인가?

다음 중 하나라도 해당하면 문서 체크 진행:
- 공식/수치/확률 변경 (데미지 공식, MOD 수치, 가챠 확률 등)
- 시스템 동작 방식 변경 (기존 메커니즘의 흐름이 달라짐)
- 새 시스템/메커니즘 추가
- enum/타입/인터페이스 구조 변경 (EMod, ModValueType 등)

다음은 문서 체크 **불필요**:
- 버그 수정 (동작 의도는 동일)
- 리팩토링 (외부 동작 동일)
- UI 레이아웃/스타일만 변경
- 단순 텍스트/설정값 수정

### 절차

1. **매칭** — `Docs/INDEX.md`의 키워드 컬럼에서 변경된 시스템과 관련된 문서를 찾는다
2. **읽기** — 관련 문서를 읽고 현재 코드와 비교한다
3. **판단** — 문서 내용이 코드와 일치하면 패스. 괴리가 있으면 갱신한다
4. **갱신** — 코드 변경에 맞게 문서를 수정한다. 변경하지 않은 부분은 건드리지 않는다
5. **보고** — 갱신한 문서 목록을 완료 보고에 포함한다

### 갱신 원칙

- 문서의 기존 형식/스타일을 유지한다
- 코드에서 읽어낼 수 있는 구현 상세(함수 시그니처, 파라미터 목록)는 쓰지 않는다
- **설계 의도, 규칙, 개념적 설명**만 갱신 대상이다
- 새 시스템 추가 시 INDEX.md에 항목이 없으면 추가한다

## 검증 실패 시

검증에서 실패가 발견되면:
1. 완료 선언 **취소**
2. 사용자에게 즉시 알림 (숨기지 마라)
3. `systematic-debugging` 4단계로 진입

## 트리거

- "완료했습니다" / "끝났습니다" / "고쳤습니다" 라고 말하기 직전
- 작업 핸드오프 / commit 직전
- 서브에이전트가 결과 보고했을 때 (에이전트 말 그대로 전달 금지 — 직접 확인 후 전달)

## 관련

- `systematic-debugging` — 검증 실패 시 발동
- `debug-logcollector` — 실제 출력 캡처
- `Docs/INDEX.md` — 6단계 문서 정합성 체크에서 참조
