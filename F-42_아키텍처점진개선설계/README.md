# F-42. 아키텍처 점진 개선 설계

**구간** Phase 3 (2026.06.12) | **포지션** TD | **AI** 협업

- **문제**: 프로젝트가 단일 `Assembly-CSharp`으로 되어 있어 **한 줄만 고쳐도 전체가 재컴파일**된다. 코드가 30만 줄에 가까워지면서 컴파일 대기가 개발 속도의 병목이 되었다. 동시에 async 처리, 이벤트 전달 등 구조적으로 개선할 여지도 쌓여 있었다.
- **해결**: 전면 리팩토링이 아니라 **점진 개선 설계**를 문서로 만들었다.
  - **asmdef를 하층부부터 분리** — 의존성이 적은 하층(유틸·타입·공유 정의)부터 어셈블리를 떼어낸다. 그리고 **효과 판정을 컴파일 시간 측정으로** 한다. "분리했으니 빨라졌을 것"이 아니라 측정으로 확인한다.
  - **분리 차단 요인을 특정** — `Logic → Hud` **역참조 17파일**. 로직이 UI를 참조하고 있으면 어셈블리를 나눌 수 없다. 이 17개가 구체적 작업 목록이 된다.
  - **UniTask 도입** + **자체 경량 EventBus**.
  - **VContainer / MessagePipe / R3는 비용 대비 이득을 논증한 뒤 명시적으로 제외**했다. 도입하지 않기로 한 이유를 문서에 남겼다.
- **기술**: Unity Assembly Definition 분리 전략, 의존성 역참조 분석, UniTask, 경량 EventBus 설계, 기술 도입 비용-편익 평가
- **정량**: `Logic→Hud` 역참조 **17파일** 특정 / 도입 3종 결정 + 제외 3종 결정
- **근거**: `Docs/plans/26.06.12_프레임워크-점진-개선-명세서.md`
- **면접 포인트**: **"도입하지 않기로 한 결정을 근거와 함께 남겼다."** VContainer(DI)·MessagePipe(메시징)·R3(리액티브)는 모두 Unity 씬에서 널리 쓰이는 좋은 라이브러리다. 그것을 **비용 대비 이득 논증 후 제외**했다는 것은 유행이 아니라 프로젝트 상황으로 판단했다는 뜻이다. 1인 개발에서 의존성 하나는 곧 학습·유지보수 비용이다. 또한 asmdef 분리 효과를 **컴파일 시간 측정으로 판정**하겠다고 미리 정한 것 — 여기서도 "검증 기준 먼저"가 반복된다.
