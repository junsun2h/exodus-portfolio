# F-28. Perforce → Git 마이그레이션

> 특정 파일로 잘라낼 수 없다. 아래 카드의 *근거* 항목이 실제 산출물이다.

**구간** Phase 3 (2026.03.11) | **포지션** TD | **AI** 협업

- **문제**: Perforce는 중앙 집중식이라 **브랜치를 가볍게 만들 수 없다.** AI와 병렬로 여러 작업을 진행하려면 작업 단위로 브랜치를 따고 버리는 것이 자유로워야 하는데, P4에서는 그 비용이 너무 크다.
- **해결**: 기존 P4 환경 구조를 먼저 문서화한 뒤(무엇을 옮기고 무엇을 버릴지 판단하기 위해), Git으로 전환하고 **AI 병렬 작업을 전제로 한 브랜치 전략**을 수립했다.
  - 전환 직후 문서 구조 정리(`26.03.11_Docs-문서-구조-정리-계획.md`)를 함께 진행 — 저장소를 바꾸는 김에 문서 배치도 정리했다.
- **기술**: Perforce depot 구조 분석, Git 이관, Unity 프로젝트 `.gitignore`/LFS 구성, 브랜치 전략 설계
- **정량**: 전환 계획 + P4 구조 분석 문서 2종 / 전환일 이전 커밋 이력은 소실 (이 문서 체계가 필요한 이유)
- **근거**:
  - `Docs/인프라/P1Git전환/26.03.11_Perforce-→-Git-전환-계획.md`
  - `Docs/인프라/P1Git전환/퍼포스/26.03.11_기존-Perforce-환경-구조.md`
  - `Docs/리팩토링/완료플랜/26.03.11_Docs-문서-구조-정리-계획.md`
- **면접 포인트**: **버전 관리 전환을 "AI와 어떻게 일할 것인가"의 관점에서 결정했다.** Git이 더 좋아서가 아니라, 병렬 작업 브랜치 비용이 AI 활용의 병목이었기 때문이다. 도구 선택을 워크플로우 요구에서 역산한 사례. (다만 전환으로 이전 이력이 소실되었고, 그것이 이 경력 문서를 코드 고고학으로 재구성하게 만든 원인이기도 하다.)
